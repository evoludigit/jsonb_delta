# jsonb_delta (binary implementations) — measured performance, Hetzner CCX13

**This artifact supersedes `benchmarks/2026-07-20-issue15-ccx13.md`**, which
measured the serde implementations shipped in v0.2.0. It also supersedes the
figures in `README.md` and `docs/PERFORMANCE.md`. Numbers here are for the
**binary implementations** (this branch, commit `5c2377d`) — the next release,
not the currently published v0.2.0.

Issue #15 asked for numbers keyed to a version and a machine profile a third
party can rent and re-run. This is that.

## What changed since the 2026-07-20 measurement

The 2026-07-20 run measured v0.2.0 (serde) and found the #15 reporter correct:
single-element update/delete at parity-to-slower vs native re-aggregation, the
ratio *falling* with array size, and `jsonb_merge_shallow` 3–7× *slower* than
`||`. The hot functions have since been rewritten to walk PostgreSQL's binary
jsonb directly instead of round-tripping through `serde_json`. This artifact is
the same matrix re-run against that rewrite.

Dedicated vCPU, not shared: steal time at the ~1 ms scale being measured is the
whole signal, not a rounding error. `speedup = native_median / delta_median`, so
> 1 means jsonb_delta is faster than the native SQL baseline.

**Single run, not two.** Unlike the 2026-07-20 artifact (mean of two runs), this
is one pass of the matrix — the host was torn down immediately to stop billing.
Within-run stability is high: p95 sits within a few percent of the median on
almost every row (e.g. update-1000-stored: median 1.382 ms, p95 1.404 ms), which
a dedicated vCPU makes believable. A confirming second run was not taken to avoid
re-provisioning; the dev-host measurements corroborate every direction below. All
eight calibration controls behaved (a sleeping arm reads 188× / 0.0017×; the two
arms-designed-to-disagree reported no ratio), so the instrument is trustworthy.

## Result 1 — the binary rewrite recovers the individual-operation win

Native baseline is `jsonb_set` + `jsonb_agg` re-aggregation, the same one the
README compares against and the same one the #15 reporter measured. Ratios > 1
mean jsonb_delta is faster.

| Operation | 10 | 50 | 100 | 1000 | (v0.2.0 serde, 2026-07-20) |
|---|---|---|---|---|---|
| update, in-memory  | 2.11× | 2.39× | 2.47× | **2.35×** | 1.56× → 0.67× |
| update, stored     | 1.76× | 1.69× | 1.66× | **2.22×** | 1.36× → 0.77× |
| delete, in-memory  | 2.03× | 2.25× | 2.47× | **3.82×** | 1.53× → 0.66× |
| delete, stored     | 1.97× | 1.66× | 1.63× | **2.06×** | 1.47× → 0.77× |

(Integer keys shown; text keys measured the same to slightly higher — e.g. update
1000 in-memory 3.93× text vs 2.35× int.)

Two things changed versus v0.2.0, and both matter:

1. **The win is real now, 1.6–3.9× depending on operation and scenario**, where
   the serde build was at parity or slower.
2. **The trend no longer inverts.** v0.2.0's ratio *fell* with array size
   (1.56× → 0.67×), exactly as the reporter's mechanical argument predicted for a
   whole-document round trip. The binary build removes that round trip, so the
   ratio holds up or rises with size instead of collapsing.

The reporter was right about v0.2.0. The mechanism they identified — parse+serialize
dominating a whole-document update — is precisely what the binary rewrite removes.

## Result 2 — shallow merge is now at parity with `||`, not 3–7× slower

| Function | Measured (binary) | v0.2.0 serde | Old published |
|---|---|---|---|
| `jsonb_merge_shallow`, 50-element doc   | **0.99× (parity)** | 0.34× | 1.5–2× |
| `jsonb_merge_shallow`, 1000-element doc | **1.04× (parity)** | 0.15× | 1.5–2× |

`||` is a built-in operating on jsonb's binary form; the serde function paid a
full parse + re-serialize to do the same job and lost 3–7×. Walking the binary
form directly brings it to parity. It is **not** a speedup over `||` and should
not be advertised as one — parity is the honest and correct claim.

## Result 3 — coalescing is still the largest win, but smaller than on serde

One `jsonb_apply_changeset` call vs a chain of N `jsonb_smart_patch_array` calls:

| Array | N | Ratio (binary) | (v0.2.0 serde) |
|---|---|---|---|
| 500  | 5  | **0.98× (parity)** | 4.74× |
| 500  | 20 | **8.05×** | 22.95× |
| 500  | 50 | **21.29×** | 52.39× |
| 5000 | 50 | **17.998×** | 71.17× |

The coalescing advantage is real and large at high op counts, but it **shrank**,
and the reason is the honest headline of this whole exercise: the binary rewrite
made the *chained alternative* cheap too. On serde, a chain of N smart_patch calls
paid N full round trips, so one changeset (one round trip) beat it 52–71×. Now
each smart_patch call is a cheap binary spine-rebuild, so the chain is far less
wasteful and the changeset's edge over it is 8–21× rather than 52–71×.

At low op counts a single changeset is at parity or **slower** than the
alternatives, because materializing the document once costs more than a couple of
spine-rebuilds:

| Scenario | Ratio |
|---|---|
| 1 edit, 200-post doc (changeset vs 1 smart_patch)  | **0.32× (slower)** |
| 2 edits, 200-post doc                              | **0.47× (slower)** |
| 4 edits, 200-post doc                              | 1.40× |
| 8 edits, 200-post doc                              | 3.02× |
| 4 edits, 100-post doc                              | **0.82× (slower)** |

## Result 4 — vs the batch primitive, it depends on N

`jsonb_apply_changeset` vs `jsonb_array_update_where_batch` (the strongest native
baseline — a single-pass N-update primitive):

| Array | N | Ratio |
|---|---|---|
| 500  | 5  | **0.57× (batch faster)** |
| 500  | 50 | 3.00× |
| 5000 | 50 | 3.59× |

`jsonb_array_update_where_batch` itself, measured against native re-aggregation
(10 updates in a 100-element array), is at **parity (1.07×)**. Its value is a
single pass; its current binary implementation scans the spec list per element
(O(elements × specs)), which is why the changeset — doing N optimized keyed
searches — overtakes it at high N. That is a batch-side optimization opportunity,
not a changeset win to advertise.

## What this means

The rule from the serde measurement still holds, but the binary rewrite moved the
line: **jsonb_delta wins where it removes a serialization the native path pays.**

- A single surgical operation now removes a serialization the native
  re-aggregation still pays (native builds the whole array with `jsonb_agg`; the
  binary function rebuilds only the changed spine). Hence 1.6–3.9×, rising with
  size — the opposite of the serde build.
- Shallow merge against `||` removes nothing `||` did not already avoid, so it is
  parity.
- Coalescing N edits into one pass removes serializations versus chaining, so it
  scales with N — but less dramatically than on serde, because chaining is now
  cheap too.
- At very low op counts the one-time materialization of a changeset is not yet
  amortized, so it is at or below parity.

So the headline is per-operation and per-scenario, not one multiplier:
**single-element update/delete are 1.6–3.9× faster than native re-aggregation and
the win grows with array size; shallow merge is at parity with `||`; and coalescing
many edits into one changeset is a large win (up to ~21×) at high op counts and a
small loss at one or two.**
